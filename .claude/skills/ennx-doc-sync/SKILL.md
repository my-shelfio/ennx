# ennx ドキュメント整合の確認

差分範囲: $ARGUMENTS（省略時は `master..develop`。タグ以降を見る場合は `v0.1.0..develop` のように指定）

git-workflow.md のワークフロー④「ドキュメント整合の確認」を担当するスキル。
リリース準備（ennx-release-draft）の前に実行することを推奨する。

## 停止・確認条件（必ず守る）

- **このスキルは検出と更新案の提示までで停止する**。ユーザーの承認を得るまで
  ドキュメントファイルを編集しない（git-workflow.md「禁止事項」: 許可なくドキュメントを
  編集しない）。
- 承認された場合も、**承認された項目だけ**を編集する。ついでの修正・体裁の整えを行わない。
- 乖離が推測に留まる場合は「要確認」として提示し、断定しない。
- エラーが発生したら停止してユーザーに報告する。勝手にリカバリーしない。

## 対象ドキュメント

| ファイル                                             | 主な検出観点                                       |
| ---------------------------------------------------- | -------------------------------------------------- |
| `docs/system-spec.md`                                | 機能・画面・API・技術スタック・制約値              |
| `docs/event-schema.md`                               | イベント種別・フィールド・feature ごとのスキーマ分割 |
| `docs/event-schema.json`                             | マッチングのイベントスキーマと実装の整合           |
| `docs/assignment-event-schema.json`                  | 割り当てのイベントスキーマと実装の整合             |
| `README.md`                                          | セットアップ手順・コマンド・ディレクトリ構成・デプロイ手順 |
| `CLAUDE.md`                                          | 品質ゲートのコマンド・アーキテクチャ方針・スキル一覧 |
| `.claude/rules/` `.claude/skills/` `.claude/agents/` | ルール間の矛盾・存在しない資料への言及             |

## 手順

### 1. 差分範囲の確定

```bash
git fetch origin
git diff --stat <差分範囲>
git log <差分範囲> --oneline
```

- 差分が 0 件の場合は「対象範囲に差分がありません」と伝えて停止する
- 進行条件: 差分範囲と変更ファイル一覧を宣言した

---

### 2. 仕様に影響する変更の抽出

差分から、ドキュメントの記述を変えうる変更だけを抽出する。抽出対象:

- **API**: `backend/src/api/`・各 feature の `presentation/`（エンドポイント・リクエスト/
  レスポンススキーマ・バリデーション上限値の増減）
- **画面**: `frontend/src/pages/`・`widgets/`・ルーティング（`shared/config/routes.ts`）・
  グローバルナビの項目
- **アルゴリズム／ドメイン**: 新しいメカニズム・feature の追加、入力制約や上限値の変更
- **イベント**: イベント種別・フィールドの追加削除、スキーマファイルの変更
- **技術スタック・コマンド**: `pyproject.toml`・`frontend/package.json`・
  `.github/workflows/`・`render.yaml` の変更
- 進行条件: 変更を上記の観点ごとに分類し、ドキュメントに影響しうる項目を列挙した

---

### 3. ドキュメントとの突き合わせ

抽出した項目ごとに、対象ドキュメントの該当箇所を読んで比較する。判定は次の 3 種類。

- **乖離**: 実装とドキュメントの記述が矛盾している（記述が古い・値が違う）
- **記載漏れ**: 実装にあるがドキュメントに記述がない
- **不要記述**: ドキュメントにあるが実装から削除されている

加えて、範囲によらず次の 2 点を横断確認する。

- **存在しない資料への言及**（documentation.md MUST 1 違反）: リポジトリに存在しない
  資料名がドキュメント・ソースコードに混入していないか
- **ソースコードからのドキュメント参照**（CLAUDE.md「コーディング規約」違反）:
  `backend/src/**/*.py`・`frontend/src/**/*.ts(x)` の docstring・コメントに
  ドキュメントファイル名やイシュー番号（`#NN`）が書かれていないか

- 進行条件: 検出結果を一覧化した（0 件の場合もその旨を宣言する）

---

### 4. 乖離一覧と更新案の提示

検出結果を、対応の要否が判断できる形で提示する。**この時点では編集しない。**

```
## ドキュメント整合の確認結果（<差分範囲>）

### 1. <ファイル名> — <乖離 / 記載漏れ / 不要記述 / 規約違反>

- 現状の記述: <該当箇所の引用>
- 実装の実態: <根拠となるファイル・値>
- 更新案: <差し替える文章>

（項目ごとに繰り返す）

検出 0 件の場合: 対象範囲でドキュメントとの乖離は検出されませんでした。

---
上記のうち、反映してよい項目を指定してください（すべて反映する場合は「すべて」）。
```

- 「更新案」は実際に置き換える文章として書く（方針の説明に留めない）
- 進行条件: ユーザーに提示し、反映可否の回答を得た

---

### 5. 承認された項目の反映

ユーザーが指定した項目のみを編集する。

- 編集後、CLAUDE.md「品質ゲート」のうち変更に関係するものを実行する
  （`docs/*.json` の変更や、コード側の修正を伴う場合は必須）
- コミットメッセージは `docs:` を使う。作業ブランチは `docs/<イシュー番号>`
  （イシューがない場合は先に ennx-issue-draft スキルで起票する）
- 「すべて却下」の場合はこのステップを飛ばす
- 進行条件: 承認された項目だけが変更されている（`git diff` で確認した）

---

### 6. 完了前チェックリスト

完了報告の前に以下を確認する。1 つでも満たさない場合は該当ステップに戻る。

- [ ] 差分範囲の全変更ファイルを検出観点に照らして確認した
- [ ] 検出した各項目に、根拠（ファイル・値）と更新案が付いている
- [ ] ユーザーの承認前にドキュメントを編集していない
- [ ] 反映した変更が承認された項目のみである

### 7. 完了報告

```
✅ ドキュメント整合の確認が完了しました

差分範囲: <差分範囲>
検出: <件数>件（乖離 <n> / 記載漏れ <n> / 不要記述 <n> / 規約違反 <n>）
反映: <件数>件
未反映: <件数>件（理由: <ユーザーの判断>）
```
