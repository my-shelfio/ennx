# ennx バグ対応

対象: $ARGUMENTS（失敗するテスト名、エラー出力、またはバグの症状）

testing.md・git-workflow.md のルールに従う。**原因を特定する前に修正案を書かない**。

## 手順

### 1. 再現

- 失敗するテスト・操作を実行し、エラーを自分の環境で再現する
  （Hypothesis の場合は Falsifying example を取得する）
- 進行条件: エラーメッセージと再現手順を記録した

### 2. 最小反例の構成

- 反例を提案者2〜3人・受入者1〜2程度まで手で縮小し、スクリプトで違反を直接確認する
- 各ラウンド・各フェーズで何が起きるかをイベントログ等で追跡し、
  「どの処理が・どの条件で・何の不変条件を破るか」を1文で言えるようにする
- 進行条件: 最小反例と発生メカニズムの説明が揃った

### 3. 理論照合と原因の切り分け

- ennx-theory-checker エージェントに「現実装の挙動と教科書の定義のどちらが正か」を
  照合依頼し、原因を次のいずれかに分類する:
  (a) 実装バグ（移植ミス） (b) 移植元由来のバグ (c) 前提条件（入力検証）の不足 (d) テスト側の誤り
- 進行条件: 分類と、教科書引用付きの根拠がある

### 4. bug イシュー登録とブランチ作成

- develop マージ済みコードのバグは bug ラベルでイシューを登録
  （再現例・原因・対応方針・受入条件を記載）し、最新 develop から `fix/<番号>` を切る
- 未マージのスタックPR 上のバグは、原因コミットを含む元ブランチで修正する（イシュー不要）
- 進行条件: 作業ブランチが規約どおりである

### 5. 修正と回帰テスト

- 分類に応じて修正する（(b) は教科書の定義どおりに、(c) は `__post_init__` の検証追加で）
- 最小反例をハードコードした回帰テストを追加（docstring にイシュー番号とメカニズムを記載）
- **既存テストの期待値は変更しない**（変更が必要な場合は理論照合に戻り、根拠を明記する）
- 進行条件: 回帰テストが修正前に失敗し修正後に通過すること、既存テストが全通過することを確認した

### 6. 品質ゲートと PR

- ennx-develop-work のステップ4〜5を実施（slow 込みの全テストも実行）

## 完了チェックリスト（全項目 yes で完了）

- [ ] 最小反例がテストにハードコードされている
- [ ] 原因分類に教科書引用または実行結果の根拠がある
- [ ] 既存テストの期待値を変更していない（変更した場合は根拠を PR に明記した）
- [ ] slow 込みの全テストが通過している
