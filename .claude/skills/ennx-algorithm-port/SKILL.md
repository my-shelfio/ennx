# ennx アルゴリズム移植

対象: $ARGUMENTS（移植元ファイル名またはアルゴリズム名）

`algorithm-port.md`・`testing.md` のルールに従う。**ステップ2と6を飛ばした移植は完了と見なさない**。

## 手順

### 1. 移植元と理論の理解

- `.claude/rules/algorithm-port.md` の該当箇所を読む
- **移植元コードと実行例（*_exec.py 相当）の提供をユーザーに依頼し、受け取ってから読む**（タスク開始時に提供済みならそれを使う。提供なしでの記憶ベース実装は禁止）
- 理論定義（アルゴリズムの定義・保証される性質・前提条件）が `.claude/rules/algorithm-port.md` にない場合は、理論情報の提供もユーザーに依頼する
- ennx-theory-checker エージェントに理論定義の要約を依頼する
- 進行条件: アルゴリズムの入出力・不変条件・理論的前提を箇条書きにした

### 2. 期待値の確定【必須ゲート】

- ennx-theory-checker エージェントに移植元実行例の実行を依頼し、全ケースの期待値（Python リテラル）を受け取る
- 進行条件: **全実行例の期待値が記録されている**（これがないまま実装に進むことは禁止）

### 3. データモデル設計

- `models.py` の既存クラス（BaseMatchingInput / DAInput / MatchingResult 等）への適合方法を決める。新規フィールドは派生クラスで追加し、理論的前提は `__post_init__` で検証
- 進行条件: 入力・結果クラスの定義（フィールドと検証項目）を確定した

### 4. 実装

- 純粋関数として実装。イベントログは docs/event-schema.md の共通スキーマで記録（新しい event_type が必要なら docs も更新）
- 進行条件: mypy strict がエラーなし

### 5. フィクスチャテスト

- ステップ2の期待値と完全一致するテストを書く（backend/tests/features/matching/domain/test_<name>.py）
- 入力バリデーションの異常系テストも書く
- 進行条件: 全フィクスチャテストが通過（**1件でも不一致なら実装を疑い、期待値は変えない**）

### 6. プロパティテスト【必須ゲート】

- backend/tests/features/matching/domain/test_properties.py に理論的性質のテストを追加（共通: 個人合理性・定員遵守 / 固有: 教科書が保証する性質 / イベント再構成一致）
- 反例が出た場合: ennx-bugfix スキルの手順（最小反例→理論照合）で対処する
- 進行条件: slow 込みの全テストが通過

### 7. 品質ゲートと PR

- ennx-develop-work のステップ4〜5（品質ゲート → reviewer → PR）を実施

- [ ] フィクスチャテストが移植元の全実行例をカバーし、期待値を一切変更していない
- [ ] 理論的前提が入力検証（ValueError）になっている
- [ ] プロパティテストが追加され slow 込みで通過している
