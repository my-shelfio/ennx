# ennx イシュー起票

要求: $ARGUMENTS（未指定の場合は「起票したい要求の内容を教えてください」と伝えて停止する）

git-workflow.md のワークフロー①「要求を整理する」を担当するスキル。起票したイシューは
ennx-develop-work スキルの入力（イシュー番号）になる。

事前に CLAUDE.md と `.claude/rules/git-workflow.md`・`documentation.md` を読むこと。

## 停止・確認条件（必ず守る）

- **起票はユーザーの承認を得てから行う**。承認前に `gh issue create` を実行しない。
- **新規ラベル・マイルストーンを作らない**（git-workflow.md「禁止事項」）。既存ラベルで
  表現できない場合はユーザーに確認する。マイルストーンは運用しない。
- **イシュー本文にドキュメントファイル名を書かない**（CLAUDE.md「コーディング規約」）。
  参照が必要な内容は自己完結した説明として本文に転記する。
- **リポジトリに存在しない資料に言及しない**（documentation.md MUST 1）。
- 調査で判明しなかった事項は推測で埋めず「未確定事項（要確認）」に記載する。
- エラーが発生したら停止してユーザーに報告する。勝手にリカバリーしない。

## 定数

- **GitHub リポジトリ**: `my-shelfio/ennx`
- **テンプレート**: `.github/ISSUE_TEMPLATE/` の Issue Forms

---

## 手順

### 1. 要求の把握と重複確認

要求を 1〜2 文に要約し、既存イシューとの重複を確認する。

```bash
gh issue list --repo my-shelfio/ennx --state all --limit 100
gh issue list --repo my-shelfio/ennx --state all --search "<要求のキーワード>"
```

- 同趣旨の既存イシューがある場合は**起票せず**、該当イシュー番号を提示して
  「既存イシューへの追記」か「別イシューとして起票」かをユーザーに確認する
- 進行条件: 要約と重複確認の結果を宣言した

---

### 2. 種別判定とテンプレート選択

要求の内容から種別を判定し、テンプレート・タイトル接頭辞・ラベル候補を決める。

| 種別                                     | テンプレート        | タイトル接頭辞 | ラベル候補                                         | prefix   |
| ---------------------------------------- | ------------------- | -------------- | -------------------------------------------------- | -------- |
| 新機能・機能改修・UI/UX 向上             | `default_issue.yml` | `【feat】`     | `feature` / `ui-ux`                                | `feat/`  |
| バグ・予期しない動作                     | `bug_report.yml`    | `【fix】`      | `bug`                                              | `fix/`   |
| 動作に影響しない変更・ツール・環境の変更 | `default_issue.yml` | `【chore】`    | `setup` / `ci` / `infra` / `test` / `nice-to-have` | `chore/` |
| ドキュメントの作成・更新・修正           | `docs.yml`          | `【docs】`     | `docs`                                             | `docs/`  |

- ラベルは prefix 判定（git-workflow.md のブランチ表）とリリースノートのカテゴリ分類
  （`.github/release.yml`）の両方に使われるため、**必ず 1 つ以上付与する**
- 実在するラベルかを確認する

```bash
gh label list --repo my-shelfio/ennx
```

- 進行条件: 種別・テンプレート・タイトル・ラベル候補を宣言した

---

### 3. 現状調査

要求に関連する既存実装をリポジトリ内で調査し、**ファイルパスと役割**を列挙する。

- バックエンドは feature（`matching` / `assignment` / `voting`）と層
  （domain / application / presentation / infrastructure）、フロントエンドは FSD の
  レイヤーを手がかりに関連箇所を洗い出す
- 変更が波及しうる箇所（API スキーマ・型生成・イベントスキーマ・テスト・import-linter 契約）を
  確認する
- 調査していない範囲を「調査済み」と書かない
- 進行条件: 関連ファイルを列挙し、変更が必要／不要の見当をつけた

---

### 4. 本文ドラフトの生成

選択したテンプレートの**全セクションの見出しをそのまま使って**本文を組み立てる。

`default_issue.yml`（機能改修・改善）の場合:

```markdown
依存: <イシュー番号 or なし>
ブロック: <イシュー番号 or なし>

## 背景・目的

<何をするか・なぜするか>

## 現状の実装（調査結果）

- `path/to/file.py` — 役割の説明

## 影響範囲

### 変更が必要

- `path/to/file.py` — 何をどう変更するか

### 新規作成が必要

-

### 削除候補

-

### 影響を受けないもの（確認済み）

- 変更不要と判断した箇所とその理由

## 作業内容（タスク分解）

1.
2.

## 未確定事項（要確認）

- なし

## 完了条件

- [ ]
- [ ]
```

`bug_report.yml` の場合は「発生事象 / 再現手順 / 期待する動作 / 根本原因 / 対応内容 /
完了条件 / 実行環境 / 参考」、`docs.yml` の場合は「背景・目的 / 対象ドキュメント /
作業内容（タスク分解）/ 完了条件」の見出しを使う。

作成時の注意:

- **完了条件は検証可能な粒度**にする（「〜が動く」ではなく「〜のコマンドが通る」「〜の画面で
  〜が表示される」など、達成の判定方法がわかる書き方）
- **依存・ブロック**は、先行して別イシューの実装が必要な場合に番号で記載する
  （依存があるイシューはブランチのベースが変わる。git-workflow.md「イシュー間で依存関係が
  ある場合PRルール」）
- 進行条件: テンプレートの必須セクションがすべて埋まった

---

### 5. ユーザー確認

タイトル・ラベル・本文ドラフトをそのまま提示し、次のように確認する。

```
以下の内容でイシューを起票してよいですか？

タイトル: <タイトル>
ラベル: <ラベル>

--- 本文 ---
<本文ドラフト>
```

- 修正指示があれば反映して再提示する
- 進行条件: ユーザーの承認を得た

---

### 6. 起票

承認された内容で起票する。本文は一時ファイル経由で渡す（改行・記号の欠落を防ぐため）。

```bash
gh issue create \
  --repo my-shelfio/ennx \
  --title "<タイトル>" \
  --label "<ラベル>" \
  --body-file <本文を書き出した一時ファイル>
```

- `--milestone` は指定しない（マイルストーンは運用しない）
- 作成後、イシュー番号と URL を取得する
- 進行条件: イシューが作成され、番号と URL を取得した

---

### 7. 完了前チェックリスト

完了報告の前に以下を確認する。1 つでも満たさない場合は該当ステップに戻る。

- [ ] 既存イシューとの重複を確認した
- [ ] タイトル接頭辞がテンプレートの形式に沿っている
- [ ] 実在するラベルが 1 つ以上付与されている（新規ラベルを作っていない）
- [ ] テンプレートの必須セクションがすべて埋まっている
- [ ] 完了条件が検証可能な粒度で書かれている
- [ ] 本文にドキュメントファイル名・存在しない資料への言及がない
- [ ] 起票前にユーザーの承認を得た

### 8. 完了報告

```
✅ イシューを起票しました

イシュー: #<番号> <タイトル>
ラベル: <ラベル>
URL: <イシューの URL>

着手する場合: /ennx-develop-work <番号>
```
