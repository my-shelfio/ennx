# 品質ゲートルール

## MUST

1. **コミット前に品質ゲートを必ず実行し、全通過させる**。コマンドは CLAUDE.md の
   「品質ゲート（コマンドの正本）」に記載のコマンド群をその順で実行する（重複記載しない）。
   frontend/ に変更がある場合は同セクションのフロントエンド用コマンドも全通過させる
2. **lint / 型 / テストの指摘を握りつぶさない**。修正は指摘が発生した変更の属するブランチで
   行う。スタックPR で先行ブランチ由来の指摘を見つけた場合は先行ブランチで修正し、再マージする
3. **CI と同一条件を保つ**。品質ゲートの内容を変える場合は .github/workflows/ci.yml と
   .pre-commit-config.yaml と CLAUDE.md を同時に更新する
4. **`--no-verify` は絶対禁止**（git-workflow.md の再掲。pre-commit は唯一の自動品質チェック）
5. **プロパティテスト（slow マーカー）に影響しうる変更**（backend/src/features/matching/domain/ 配下の
   変更）では、ローカルでも slow 込みの全件テストを実行してからコミットする

## 根拠

品質ゲートは「実装の完了」の客観的な定義である。モデルや作業者の自己判断で「動くはず」と
省略すると、CI で落ちて後続のスタックPR 全体が滞る。M2 では全ブランチでゲートを通し続けた
ことで、6本の PR を修正なしでマージできる状態に保てた。

## 実例

EventType の `str, Enum` 継承は ruff UP042（StrEnum を使え）で検出された。指摘は発生元の
feat/6 ブランチで修正し、後続の feat/21・feat/22・chore/8 に再マージして全ブランチを
通過状態に保った。
