# アルゴリズム移植・実装ルール

## MUST

1. **移植前に移植元を実行して期待値を確定する**。移植元の実行例（*_exec.py 相当）をverbose=False で実行し、全例の proposer_match / receiver_match 等を記録してから実装を始める。期待値はフィクスチャテストとして backend/tests/features/matching/domain/ に固定する。**記憶ベースで実装せず移植元コードと実行例の提供をユーザーに依頼する**
2. **理論定義を正とする**。実装判断に迷ったら下記の[アルゴリズム理論の定義](./algorithm-port.md#アルゴリズム理論)に立ち返り、記載がなければ理論情報の提供をユーザーに依頼する。移植元コードと理論定義が食い違う可能性がある場合は移植元のバグを疑い、ennx-theory-checker エージェントで引用付きの照合を行ってから判断する
3. **純粋関数として実装する**。print / verbose を持ち込まない。実行過程はdocs/event-schema.md の共通イベントスキーマで記録する
4. **共通データモデルを再利用する**。入力は `models.BaseMatchingInput` 派生、結果は`MatchingResult` 派生。インデックス規約・検証方針は `CLAUDE.md`「アルゴリズム層の設計原則」に従う
5. **理論的前提を入力検証で保証する**。アルゴリズムの正しさが暗黙の前提条件に依存する場合、その条件を `__post_init__` の ValueError として明示する
6. 移植済みの3つのアルゴリズムの期待値（移植元実行例と同一結果）は `backend/tests/features/matching/domain/test_da.py` / `test_fda.py` / `test_ca.py` に固定済み。**期待値の変更には理論照合による根拠を必須とする**

## 根拠

移植元のコードには理論とズレたバグが潜在するとする。期待値の事前確定は「移植の正しさ」の判定基準を実装前に固定するためであり、理論照合は「移植元と同じ挙動 = 正しい」とは限らないケースを検出するために必要。

## アルゴリズム理論

本リポジトリのマッチングアルゴリズム（DA・FDA・CA）の定義・保証される性質・前提条件をまとめる。

【**位置づけ**】本書はリポジトリ内の理論の一次資料であり、実装・レビュー・バグ調査の理論照合は本書を第一参照とする。本書に記載のない理論情報（新規アルゴリズムの定義・移植元コード等）が必要な場合は、**ユーザーに提供を依頼する**（記憶ベースでの補完は禁止）。移植元実行例の期待値は`backend/tests/features/matching/domain/` のフィクスチャテストに固定済みで、これが移植の正しさの正である。

### 共通の用語とモデル

- **提案者（proposer）/ 受入者（receiver）**: 多対1マッチングの応募側／受け入れ側（社員／部署、研修医／病院、学生／大学）
- **選好リスト**: 外部入力は 1-indexed の相手番号を好きな順に並べたリスト。**リストに含まれない相手は「受け入れ不可能」** を意味する（部分リスト可）
- **マッチング**: `proposer_match[i]` = マッチした受入者の 0-index（-1 = 未マッチ）、`receiver_match[j]` = マッチした提案者の 0-index リスト

### 性質の定義（検証は `backend/src/features/matching/domain/checks.py`）

| 性質                       | 定義                                                                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 個人合理性（IR）           | 各エージェントのマッチ相手が自身の選好リストに含まれる（未マッチは違反でない）                                                                                                                 |
| 定員遵守                   | 各受入者のマッチ数 ≤ 定員                                                                                                                                                                      |
| ブロッキングペア (p, r)    | (1) p が r を現在の相手より厳密に好み、かつ (2) r に空き定員がある、または r が p を最悪マッチ相手より厳密に好む                                                                               |
| 安定性                     | IR + ブロッキングペアなし。安定 ⇒ 効率的（対偶: 非効率 ⇒ 不安定）                                                                                                                              |
| 弱安定性（地域上限モデル） | 実行可能性 + IR + 「許容されないブロッキングペアなし」。ブロッキングペア (p,r) が許容されるのは (a) r の地域が地域上限で満員、かつ (b) r が現採用者全員を p より好む、の両方が成立するときのみ |
| 公平性                     | 正当な羨望を持つ提案者がいない。i が j を正当に羨む ⇔ i が μ(j) を μ(i) より好み、かつ受入者 μ(j) も j より i を優先する                                                                       |
| 耐戦略性（提案者側）       | どの提案者も虚偽の選好申告で厳密に良い結果を得られない                                                                                                                                         |

### DA（Deferred Acceptance / 受入保留方式）

- **対象**: 定員制約付き多対1マッチング
- **手順**（各ラウンド）: 
  1. 未マッチの提案者が次順位の受け入れ可能な相手に提案
  2. 各受入者は「新規応募者 + 仮受入中の提案者」から優先順位の高い順に**定員まで**仮受入し、溢れた者を拒否する（受入は最終ラウンドまで確定しない = 保留）
  3. 応募が尽きるまで繰り返す
- **保証**: 提案者最適な安定マッチング（Gale and Shapley, 1962）。提案者側耐戦略性を満たす

### FDA（Flexible Deferred Acceptance / 柔軟な受入保留方式）

- **対象**: 定員に加え「地域（グループ）ごとの受け入れ上限」を持つ多対1マッチング（日本の研修医マッチング）。JRMP メカニズム（目標定員で単純に切る方式）の非効率性を解消する
- **入力**: 目標定員 `capacities`・設置上限 `max_caps`（物理上限）・地域 `regions`・地域上限 `regional_caps`・指名順序 `nomination_order`
- **前提条件（実行可能性）**: 各地域について**目標定員の合計 ≤ 地域上限**。この前提は `FDAInput.__post_init__` で検証する（破ると地域上限超過が起こりうる）
- **手順**（各ラウンド）:
  1. **提案フェーズ**: 未マッチの提案者が次順位の受け入れ可能な受入者に応募する
  2. **レギュラーフェーズ**: 各受入者は「応募者 + **すでにキープしている提案者**」から優先順位順に**目標定員の範囲内で**キープし直す。受け入れ可能だが目標定員を超えた者は即時拒否せず**待機リスト**に加える（設置上限を超える分は拒否）。
  ※ 前ラウンドの繰り上げで目標定員を超えてキープ中の者も、ここで一旦待機リストに戻る。この「キープし直し」を省略すると繰り上げ分が地域枠を占有したまま残り、後続の受入で地域上限を超過する（過去に発見された回帰バグの修正点）
  3. **待機リストフェーズ**: 指名順序に従い各受入者が待機リストから最優先の提案者を**1人ずつ**、設置上限と**地域上限の範囲内で**キープする（輪番方式）
  4. 上記の過程を地域上限が満員になるか誰も指名できなくなるまで繰り返し、キープされなかった待機者は拒否する
- **保証**: 制約付き効率性・制約付き安定性（= 弱安定性）・提案者側耐戦略性（Kamada and Kojima, 2015）。通常の安定性は保証されない（地域上限が binding の場合）

### CA（Cutoff Adjustment / カットオフ調整）

- **対象**: 一般上限制約付き多対1マッチング（定員・予算・NGペア分離・属性人数などの複合制約）
- **理論**: 各受入者の「足切りライン」= カットオフ $p$（市場価格に相当）。
  - 需要 $D_r(p)$ = カットオフのもとで $r$ を最も好む足切り通過提案者の集合。
  - 調整関数 $T$: 需要が制約違反の受入者のカットオフを$+1$。$T$ の**最小不動点**（タルスキの不動点定理）における需要が求めるマッチング
- **前提条件（遺伝性）**: 各制約は**遺伝性（hereditary）を満たす上限制約**であること（実行可能な集合の任意の部分集合も実行可能。とくに空集合は常に実行可能）。「最低◯人」等の**下限制約は対象外**（収束しない・誤った結果になりうる）。空集合の実行可能性は `CAInput.__post_init__` で検証する
- **保証**: 提案者最適**公平**マッチング（Kamada and Kojima, 2024）。提案者側耐戦略性を満たす。定員制約のみの場合、結果は DA と一致する（プロパティテストで検証済み）
